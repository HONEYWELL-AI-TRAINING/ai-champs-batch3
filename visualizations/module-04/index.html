Part 2 · Anatomy of a Good Specification

Switch blocks off to see what the model would have to guess. The refund-order content is illustrative.

Include in the spec
Users & scenariosUS1 (P1): As a support agent, I can refund a paid order so that customers are made whole quickly.
Functional requirementsFR-3: A support agent MUST be able to refund a Paid order up to its original amount.
Non-functional constraintsNFR-1: Every refund is audit-logged; only authorised roles may refund.
Interfaces & contractsPOST /orders/{id}/refund → 200 OK | 422 REFUND_EXCEEDS_TOTAL
Acceptance criteriaAC: Given a Paid order of 100, When an agent refunds 150, Then the request is rejected with error REFUND_EXCEEDS_TOTAL.
Out of scope & open questionsOUT OF SCOPE: item-level refunds. [NEEDS CLARIFICATION: partial refunds?]
6 of 6 blocks included

    Who does what · testable MUST statements · performance, security, compliance, platform · APIs, schemas, events, error shapes · Given / When / Then · what we deliberately do not build, and what is unclear.

    Could a stranger write a test from each line without asking you a question? If not, it is not specific enough.

    weak-requirement.md
    Users should be able to refund orders
quickly and securely.

// vague · untestable · no limits
    strong-requirement.md
    FR-3: A support agent MUST be able to refund a
  Paid order up to its original amount.
AC: Given a Paid order of 100,
  When agent refunds 150, Then request is
  rejected with error REFUND_EXCEEDS_TOTAL.

    Part 3 · The SDD Tool Landscape

    Different tools put the spec in different places. Know what each one is optimised for. Select a tool.

    Common thread: all six keep intent in versioned text files that humans review and agents read. They differ in workflow shape, agent support and how much process they impose.

    Match the tool to the shape of the work, not to the hype.

    ⚠ Brownfield reality
    • Recover the implicit spec first (what does it do today?)
    • Make impact analysis and regression criteria explicit
    • Iterate — don't expect a perfect upfront spec
    Today: we use Spec Kit for the lab. The same habits — explicit intent, review gates, traceability — transfer to any of these tools. Module 05 returns to brownfield work.

      Step 1 · /speckit.constitution — project-wide, written once

      memory/constitution.md (illustrative)
      ## Principles
1. Test-first: no task is done without a
   passing test for its acceptance criteria
2. Layered: controllers → services → repos
3. Public APIs are versioned and documented
4. No new dependency without a recorded reason

## Governance
Amendments need a PR and a reviewer.

      Step 2 · /speckit.specify — per feature

      specs/001-refund-orders/spec.md (illustrative)
      ## User story 1 (P1)
As a support agent, I can refund a paid order
so that customers are made whole quickly.

## Requirements
FR-1 Refund <= original amount
FR-2 Only orders in status Paid
[NEEDS CLARIFICATION: partial refunds?]

        Every later plan is checked against it.

        Spec = what and why

        Leave the tech stack out; that is the plan's job.

        Mark unknowns

        Best practice: describe the outcome and the user, not the implementation. If your spec names a framework, you have started the plan too early.

        Best practice: tell the plan your tech choices and constraints explicitly (stack, existing services, limits). If you don't, the model picks for you — review the plan like an architecture proposal.

        Three cheap checks that catch problems before any code exists.

        /speckit.clarify

        After specify, before plan
        Asks up to five targeted questions about gaps and ambiguity, then records your answers in a Clarifications section of the spec.
        You get: fewer silent assumptions.

        /speckit.checklist

        Anytime after specify
        Generates checklists that test the requirements themselves: complete, clear, consistent, measurable.
        You get: requirements quality, not code quality.

        /speckit.analyze

        After tasks, before implement
        Read-only scan across spec, plan and tasks for gaps, inconsistencies and constitution violations. Changes no files.
        You get: a report to act on.

        Try it · which gate catches it?

        Best practice: a wrong line in a spec costs minutes to fix; the same gap found in code costs a review cycle and a rewrite. Treat these gates as mandatory, not optional.
