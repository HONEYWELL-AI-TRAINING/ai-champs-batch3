Part 3 · Brownfield: Change Without Breaking

Before you can write a change spec, recover what the system already does. Work through the digs left to right.

⚠ Treat it as a hypothesis. AI summaries of legacy code can sound certain and be wrong. The as-is spec stays a hypothesis until a test confirms it. Ask Copilot to explore in a subagent or fresh chat and return a summary with file references; then verify by reading the code yourself.

Best practice: keep exploration output small and file-backed (Module 03: SCOPE and COMPRESS). A one-page as-is spec beats a 40-page chat transcript.

Change-impact analysis asks: what else could this change touch? Work outward in rings, and give every ring a guard.

Dependency-analysis tools, IDE “find usages” and Copilot's codebase search each find different edges — use more than one, and record what you checked. Rings 3–4 are where AI-assisted changes usually break things silently.

    • No general-purpose, GA tool translates one language to another reliably (for example C++ to .NET).
    • AI accelerates each slice; humans own the design and the parity proof.

    Situations are illustrative, written for this exercise.

    A facade routes each request to legacy or new. Traffic shifts gradually; legacy retires last. Clients keep the same URLs throughout.

    Example rollout of one slice

    Check errors and latency against the baseline at each step; roll back if they drift.

    Best practice: retire legacy code only after the new path has run at 100% for at least one release cycle. Until then, the legacy route is your rollback.
