Module 07: MCP-Enabled Workflows & Custom MCP Server Creation

Give your agents safe, governed access to repositories, docs and enterprise systems. Learn what MCP is, integrate it in Copilot, run a real workflow, then build and govern a custom MCP server.

Your Map for the Three Hours

From the concept, to integration, to a working workflow, to building and governing your own server. Select a stop to jump to its first card.

Why this matters: an agent is only as useful as what it can reach, and only as safe as the limits you put on that reach. MCP is the standard way to do both. This is the first module of the EXTEND phase: tool results are context (Module 03: select, compress, scope), specs and tests from Modules 04–06 are what an MCP workflow validates against, and M08 (PR review agents) and M10 (code agents and RAG) reuse MCP servers and need the same governance.

Part 1 · MCP Concepts & Architecture

Every AI app connecting to every tool used to mean custom glue for each pair. Set the size of your estate and compare. The deck's example is 3 apps and 3 tools; real estates have far more.

With MCP

Think of it as: a common plug for AI apps and tools. Build or approve a server once; any MCP-capable host can use it.

One client per server inside the host. Servers can run on your machine or remotely. Select a server to follow its path.

Two transports: stdio for local servers (a process on your machine) and Streamable HTTP for remote servers (reachable by URL, usually with OAuth). The protocol on top is the same for both.

Try it · which transport?

Three things a server can expose. Who decides when each is used is what tells them apart.

ToolsActions the model can call. Model-controlled.
create_issue(title, body)
get_workflow_run(id)
search_code(query)
ResourcesData the app can read as context. Application-controlled.
file:///repo/README.md
db://schema/orders
docs://api/v2/overview
PromptsReusable templates a user can invoke. User-controlled.
/review-pr
/explain-failure
/draft-release-notes

Examples are the deck's illustrative ones.

Rule of thumb: if the model should decide to do it, make it a tool. If it is just context, make it a resource. If a human triggers it, make it a prompt.

Try it · elicitation: ask the user instead of guessing

Client feature: a server can ask the user for missing input mid-task. Hosts differ in which features they support.

    Part 4 · Designing a Custom MCP Server
    

        
    
            
    
                
            
    
            
    
                
    
                    
    Build a server when an approved one does not exist for your system — and keep it small.
    
                    
    
                        
    Is there an approved server for it?→ Reuse it
    
                        
    Does it need only a few operations?→ Build small
    
                        
    Does it touch production data?→ Review first
    
                    
    
                    
    
                        
    
                        
    
                        
    
                        
                    
    

                    
    Five tool design principles
    
                    
    
                        
    One tool, one jobClear name, narrow purpose
    
                        
    Describe it for the modelThe description is the instruction
    
                        
    Typed, validated inputsReject bad arguments early
    
                        
    Small, structured outputReturn what is needed, not a dump
    
                        
    Safe by defaultRead-only unless writes are essential
    
                    
    

                    
    Sort it · good tool design or anti-pattern? (illustrative proposals)
    
                    
    
                    
    

                    
    Try it · what does the model get to do?
    
                    
    
                        
                        
                    
    
                    
    Pick an option.
    
                    
    Anti-pattern: a single run_query(sql) or run_command(cmd) tool hands the model your whole system. Expose the three questions you actually need answered.

    server.py (illustrative)
    from fastmcp import FastMCP
mcp = FastMCP("Build Tools")

@mcp.tool
def get_build_status(build_id: str) -> dict:
    """Return status and failing step for a build.
    Read-only. build_id looks like 'b-1234'."""
    if not build_id.startswith("b-"):
        raise ValueError("invalid build id")
    # call your real build API here
    return {"id": build_id, "status": "failed",
            "step": "unit-tests"}

if __name__ == "__main__":  mcp.run()
