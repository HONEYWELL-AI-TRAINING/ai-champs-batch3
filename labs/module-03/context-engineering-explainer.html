Context Engineering & Optimization Techniques

Module 03 — selecting, compressing, and scoping what you feed the model so output quality goes up while token cost stays flat.

Interactive Concept Guide

Concept

Prompt engineering shapes how you ask — framing, role, constraints, examples. Context engineering decides what the model knows about your repository before the prompt is ever sent. The second is what every later module depends on.

Stage 1 · Prompt-only
One well-worded prompt, no repo context. Fine for small self-contained tasks; breaks on anything touching existing code
→
Stage 2 · Structured prompting
Frame + role + constraints + example applied consistently. Repeatable, but still no persistent view of the repo
→
Stage 3 · Context-engineered
Repo, design, and contract context deliberately selected, compressed, and scoped before the prompt

A prompt-only pass on GET /api/tasks/stats typically ships the wrong status keys after four iterations. A context-engineered pass is right the first time — for a little more up-front context.

The model has a limited attention budget, and every irrelevant file you attach spends it — on every turn. A sharp 800-token context beats a vague 8,000-token one, at a tenth of the cost.

Everything outside the innermost box is available but deliberately not sent. Drawing this boundary task by task is what keeps token usage predictable.

Techniques · Select → Compress → Scope

The select test: "If I remove this, could Copilot get the task wrong in a way the other context wouldn't catch?" If no → reject. The selected list should be 3–5 items, not 10.

✅ Keep — names a failure it prevents

  • copilot-instructions.md — layer rules, error contract
  • The repository-layer file — the pattern the count query must follow
  • The existing list handler — response & error style to mirror
  • The ~6 contract lines — the status enum and JSON shape

❌ Reject — nothing else catches nothing new

  • Service layer — thin pass-through, the repo file already shows it
  • schema.sql — no schema change in this task
  • Frontend — no UI change
  • Other backends — parity is a later check, not context

Discovery tip: ask #codebase "which files would I change, and which is the best pattern to copy? Paths only" — then verify each path and attach the good ones explicitly. Good for discovery, worse for precision.

Practice · Measure & Bottle It

"Context engineering is worth it" is an opinion until you have numbers. Score the same task twice — prompt-only vs context-engineered — on quality, tokens, iterations, and time.

Rough estimate for comparing two contexts (~4 chars / token)
tools/estimate-tokens.sh .github/copilot-instructions.md \
  backend-python/repositories/task_repository.py \
  backend-python/routers/tasks.py \
  backend-python/tests/test_tasks_api.py

# TOTAL   ~3,900 tokens   (raw sources)
# brief   ~380 tokens     (10x smaller — same result)

For exact counts: the VS Code chat context gauge, or npx @anthropic-ai/tokenizer <file>. The ratio matters, not the precision — and prompt-only usually costs more total tokens once you add up its iteration prompts and re-reads.

Turn "attach exactly these" from a lucky prompt into a team habit with an artifact behind it.

.github/prompts/context-brief.prompt.md — the fixed structure it enforces
## Rules        3–6 lines of copilot-instructions.md that bind this task
## Contract     exact API shape, fields, types, status codes (≤ 6 lines)
## Pattern      the one file/function to mirror — path + one line
## Test         the one test file + the 1–2 cases to add
## Non-goals    what this task must NOT change

Total brief ≤ 400 tokens. If it won't fit, the task is too big — split it.

CONTEXT.md records the per-task routine (run /context-brief, attach only its output, add more only if that fails) plus what's usually enough and what to leave out. An optional shared Copilot Space is CONTEXT.md as reusable, shareable context.

Optimization — Do This / Not That

The habits that keep a context sharp, and the ones that quietly inflate token cost without improving output.

✅ Do this

  • Keep a file only if you can name a bug it prevents that nothing else catches
  • Quote the 3–6 binding lines; reference files instead of pasting them
  • Put decision-relevant lines first — truncation eats the bottom
  • New chat when the task changes; state non-goals explicitly
  • Reproduce the result with less, then keep the smaller context

❌ Not that

  • Attach whole files when a #selection would do
  • Re-send the same context on every follow-up turn
  • Copy entire specs or issue threads verbatim into the prompt
  • Let context accumulate across unrelated tasks in one session
  • Reach for a big-context model before a tight brief has failed

Worked Example · GET /api/tasks/stats

The three moves applied to one real feature — a counts-by-status endpoint. Pick a move.

Selected (4): repo instructions, the repository-layer file, the existing list handler, the ~6 API-contract lines. Test file optional.

Rejected: service layer (thin pass-through), schema.sql (no schema change), frontend (no UI), the other two backends (parity is a later check), issue history (nothing relevant).

Raw selected sources: ~3,900 tokens. The compressed brief quotes only: the layer rule, the error-contract line, the schema-owner line, the todo / in-progress / done enum, the JSON shape, total == sum, the one pattern function, and the one test case.

Result: ~380 tokens — about 10× smaller, same rubric score.

Non-goals stated: no frontend change, no change to GET /api/tasks, no new columns.

Session: fresh chat, brief attached alone (instruction file still active), nothing carried from the previous task. Add more context only if the brief-only run fails — and if it does, that missing line was load-bearing: add it to the brief.
