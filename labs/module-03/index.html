Module 03: Prompt Engineering Recap & Context Engineering

A recap of the practical prompting moves, then selecting, structuring, layering, and compressing the context supplied to AI — without letting token usage inflate.

Interactive Concept Guide

Key Concepts

The practical sequence behind any well-formed prompt, before context engineering is added on top.

1 · Frame the task
State the goal in one clear sentence — what should exist when it is done
→
2 · Set role & instruction
Tell the model what perspective to take and how to approach it
→
3 · Add constraints
Name the limits — language, style, performance, interfaces
→
4 · Give examples
Show, don't just tell — a short example anchors format and quality
→
5 · Decompose
Break a large task into smaller, independently verifiable steps
→
6 · Iterate & verify
Check the output against the goal; refine the prompt, don't accept the first pass

These six moves are necessary but not sufficient — they shape how you ask, but say nothing about what the model knows about your repository. That is what context engineering adds next.

Three maturity stages. This module moves the team from left to right.

Stage 1 · Prompt-only
One well-worded prompt, no repository context. Works for small, self-contained tasks; breaks on anything touching existing code
→
Stage 2 · Structured prompting
The six moves applied consistently. More repeatable, but still no persistent view of the repository
→
Stage 3 · Context-engineered
Repository, design, API, and spec context deliberately selected, layered, compressed, and scoped before the prompt is sent

Everything a task's context could draw from, before any selection happens. Each source is a candidate — the discipline is choosing which ones actually belong in a given task's prompt.

Selection, layering, and compression are not optional polish — skipping them is exactly how context inflation and avoidable token cost happen at scale.

Everything outside the innermost box is available, but deliberately not sent. Drawing this boundary task by task is what keeps token usage predictable — the opposite of letting context grow by default.

Anti-Patterns: How Context Inflation Happens

The habits that quietly grow token usage without improving output quality.

✅ Do this

  • Select only the files / snippets the task actually touches
  • Reuse or reference prior context instead of re-sending it
  • Summarize specs and issues to the parts that matter
  • Reset or scope context when the task changes
  • Compress deliberately — a smaller, sharper context beats a bigger, vaguer one

❌ Not that

  • Attach whole files when only a few functions are relevant
  • Re-send the same context on every follow-up turn
  • Copy entire specs or issue threads verbatim into the prompt
  • Let context accumulate across an unrelated multi-task session
  • Skip compression because the model "has a big context window"

Prompt-Only vs Context-Engineered: What the Lab Measures

The hands-on lab solves the same task both ways and compares the results on four measures. Both passes log token usage on the same worksheet — this module's baseline for every later module's cost discussion.

Prompt-only: the first-pass output is assessed as-is.

Context-engineered: the output is assessed against the same rubric — the comparison is like-for-like, not "the AI tried harder."

Both passes log token usage from the worksheet. Context engineering can lower total tokens even though it adds context up front, because it removes re-explaining and re-sending across iterations.

Iteration count is the number of back-and-forth rounds to reach an acceptable result. Prompt-only typically needs more rounds because the model keeps rediscovering repository facts.

Task completion time is measured end to end for each approach — the practical bottom line the other three measures roll up into.
