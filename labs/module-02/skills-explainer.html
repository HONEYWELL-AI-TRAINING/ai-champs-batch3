Agent Skills — Reusable Capability Packages

Module 02 · Lab 04 — how a folder with a SKILL.md, reference notes, and helper scripts turns team know-how into a versioned, model-invoked capability every agent surface can use.

Interactive Concept Guide

Concept

A skill is a self-contained capability package the model pulls in on its own when a task matches its description. It can bundle scripts and data, not just text — so it captures a whole procedure, not a rule or a snippet.

A skill is…

  • Model-invoked — the agent decides to use it
  • Self-contained — procedure + references + scripts in one folder
  • On-demand — loaded only when a task matches
  • Versioned — reviewed in a PR, travels with the repo

…the missing piece

  • Instructions (Lab 01) are always on
  • Prompt files (Lab 02) are a person's choice
  • Chat modes (Lab 03) are a person's choice
  • Only a skill is picked by the model and carries runnable files

It turns "ask Priya, she knows how we do cross-backend ports" into an artifact every agent surface — CLI, agent mode, the coding agent — can use.

Only the one-line description is always in context. The body and files load on demand — so a repo can ship many skills without bloating every prompt.

What loads, and when
description (frontmatter)   ALWAYS      lets the agent judge relevance
SKILL.md body              ON TRIGGER  the actual procedure
bundled files              ON DEMAND   detail, data, runnable scripts

That one line is the only thing the agent sees when deciding whether to use the skill. It has to match how people actually phrase the task — concrete verbs + nouns, and the trigger conditions.

✅ Sharp — gets used

  • "Port a Task Board endpoint from one backend to another so both return byte-identical JSON. Use when a change exists in one backend and must be mirrored in another, or when checking cross-backend parity."

❌ Vague — ignored

  • "Helps with backend work."
  • "Useful for endpoints."
  • "Port stuff between services."

If the agent never uses the skill, the description is almost always why — make it echo the verbs and nouns you use in the request (port, backend, parity).

Structure

One folder per skill, discovered by Copilot under .github/skills/. The Lab 04 example — port-endpoint:

.github/skills/port-endpoint/
port-endpoint/
├── SKILL.md            # YAML frontmatter (name, description) + the procedure
├── contract-notes.md   # reference the body tells the agent to read
└── scripts/
    ├── compare-responses.sh    # bundled helper (macOS / Linux)
    └── compare-responses.ps1   # bundled helper (Windows)

Frontmatter carries the name and the trigger-worthy description. The body is just the procedure — push detail into bundled files it references, or an over-long body gets ignored.

.github/skills/port-endpoint/SKILL.md
---
name: port-endpoint
description: >-
  Port a Task Board endpoint or feature from one backend (.NET, Python,
  or Java) to another so both return byte-identical JSON for the same
  request. Use when a change exists in one backend and must be mirrored
  in another, or when checking cross-backend parity.
---

# Port a Task Board endpoint between backends

## When to use
- A feature exists in one backend and must be added to another.
- You need to verify two backends agree on the same request/response.

## Procedure
1. Read the source — repository, service, controller/router layers.
2. Read the target's idioms — match framework style and error mapping.
3. Reproduce layer by layer, obeying .github/copilot-instructions.md.
4. Match the JSON contract exactly (see contract-notes.md).
5. Mirror the tests in the target's framework.
6. Verify with scripts/compare-responses.sh <path>.
7. Reconcile any diff until output is identical.

## Definition of done
- Feature implemented across all three layers; target tests pass.
- compare-responses shows identical output for every affected route.

Is a Skill the Right Fit?

Skills are one rung of the customization ladder — powerful for triggered procedures, wrong for always-on rules.

✅ Use a skill when…

  • A multi-step procedure recurs across tasks
  • It needs bundled scripts or reference data, not just text
  • It should trigger automatically on matching work
  • The same know-how is needed across CLI, agent mode, and the coding agent

❌ Reach for something else when…

  • A rule should always apply → repository / path instructions
  • A person will deliberately pick it each time → prompt file
  • You need to fix tools + model for a category of work → custom chat mode
  • It's a genuine one-off → just write the prompt

Skills in the Customization Ladder

The four Module 02 mechanisms, side by side. Pick one.

File: .github/copilot-instructions.md, AGENTS.md, .github/instructions/*.instructions.md

Loaded: automatically — every request (repo-wide) or every request touching files that match an applyTo glob.

Best for: "what good looks like here" — architecture rules, the error contract, the schema owner. Always on, no one chooses it.

File: .github/prompts/NAME.prompt.md

Invoked: by a person typing /NAME in Copilot Chat.

Best for: a repetitive request standardised as a reviewed slash-command — /new-endpoint, /write-tests, /review-diff.

File: .github/chatmodes/NAME.chatmode.md (and .github/agents/NAME.md for the coding agent)

Invoked: by a person choosing the mode from the chat dropdown.

Best for: a scoped persona that fixes instructions + allowed tools + model — a read-only API Reviewer, a test-files-only Test Author.

File: .github/skills/NAME/SKILL.md + bundled reference notes and scripts

Invoked: by the model — it matches the task to the skill's description (or you point at the path).

Best for: a multi-step procedure that carries runnable scripts and data, reused across every agent surface — "how we port a feature so the JSON stays byte-identical."
