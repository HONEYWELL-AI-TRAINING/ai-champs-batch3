The Minimal-Change Strategy

Once the blast radius is known, discipline is what keeps it small.

✅ Minimal-change strategy

  • Change only what the feature actually requires
  • Stay within the identified blast radius
  • Follow the codebase's existing patterns, even if imperfect
  • Re-run the full existing test suite before and after

❌ Maximal disruption

  • Refactor broadly while implementing the feature
  • Touch files outside the change's actual scope
  • Introduce new patterns alongside the existing ones
  • Skip re-running the existing test suite

Greenfield vs Brownfield: Where the Workflows Diverge

Same discipline, different starting constraints. Pick a dimension to compare.

Greenfield: a blank slate, guided by the spec.

Brownfield: an existing codebase, guided by the spec and existing patterns.

Greenfield: architecture & conventions.

Brownfield: repository archaeology — you cannot design conventions that already exist.

Greenfield: under-specifying requirements.

Brownfield: unintended regression — breaking something that already worked.

Greenfield: bounded by the spec.

Brownfield: bounded by the spec and the blast radius.

Greenfield: acceptance criteria.

Brownfield: acceptance criteria + the full regression suite passing.
