A versioned specification fixes all four: requirements captured once, every task traceable to intent, acceptance criteria written and checkable, and changes that flow through the spec so plan and tasks stay in sync.

Four parts, every one load-bearing for what comes next. The plan is derived from requirements and constraints; the tasks from the plan; and every task is only "done" when it satisfies its acceptance criteria.

A specification is "good enough" when it is unambiguous (one reasonable interpretation), testable (every acceptance criterion checkable mechanically or by clear manual steps), traceable (each requirement maps to tasks, code, and tests), and complete (functional and non-functional constraints both captured — not just the happy path).

A forward path from intent to working code, closed by a feedback loop back to the specification.

Validate
Check each result against the spec's acceptance criteria

Nothing moves forward without what came before it, and nothing changes without flowing back through the spec — that discipline is what makes the output traceable, not just fast. Spec changes are never edited ad hoc downstream in plan, tasks, or code.

The same four-stage flow, viewed through the versioned artifacts that carry it. Every artifact is versioned alongside the code — the specification is not a document that goes stale, it is part of the traceable record.

Prompt-Only vs Spec-Driven

The same shift Module 03 introduced for context, now applied to the whole feature.

❌ Prompt-only

  • Requirements interpreted differently each time you ask
  • No persistent artifact tying code back to intent
  • Acceptance criteria exist only in the requester's head
  • Any change means re-explaining the task from scratch

✅ Spec-driven

  • Requirements captured once, precisely, in a specification
  • Every task traces back to the spec and its acceptance criteria
  • Acceptance criteria are explicit, written, and checkable
  • Changes flow through the spec — plan and tasks stay in sync

Spec-Driven vs Prompt-Only: What the Lab Measures

The hands-on lab builds the same feature both ways and compares them on four measures.

Prompt-only: requirements are restated conversationally each time, and drift between retellings.

Spec-driven: requirements are captured once in a versioned specification and referenced, not repeated.

Prompt-only: not tracked — there is no link from a line of code back to the requirement it serves.

Spec-driven: requirement → task → implementation → test, each link explicit and checkable.

Prompt-only: ad hoc, subjective review — "looks right to me."

Spec-driven: checked against explicit acceptance criteria written before implementation started.

Prompt-only: re-explain the task from scratch and hope the new version matches the old intent.

Spec-driven: update the spec; the plan and tasks are revised from it. This is the change-resilience the lab measures directly.
